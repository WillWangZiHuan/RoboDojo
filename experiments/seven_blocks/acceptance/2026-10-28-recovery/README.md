# 连接停滞修复验收（2026-10-28）

**已验证的是运行器持久性与静默恢复，不是模型自主展示完成。**

旧 Astra 物理轮 Slurm 48825 在 53 次模型工具请求后停滞。模型独立小请求正常，原长历史请求出现 Broken pipe；根因尚不能归结为已确认的网络波动。旧版 SSH+srun 进程链的接管未保住输入寿命，最终 episode 为 interrupted，原因 input closed without submission。该轮三路连续 MP4 和 168 张相机 PNG 已保存本地，不能记作主动提交。

新架构使用独立 sbatch 作业，批处理进程持有 O_RDWR FIFO，持久保存原生回复。本地桥接主动被杀掉后，Slurm 48918 仍存活；重连后的所有物体、关节、TCP、动作数、物理步数和重置次数逐项相等。测试在模型启动前进行，动作/物理步/重置均为 0，未改变七块初始场景。

合成客户端测试验证 600 秒静默守护逻辑（测试用 60 秒阈值）：存在未完成物理请求时不重启；请求完成后恢复原 thread ID，且不重放动作。测试不调用真实模型或物理仿真。测试报告见本目录两个 acceptance JSON。

Astra 新轮从相同初始场景与原始指令、全新模型上下文独立开始；后续 Sol、Terra 还须各完成一次。全部过程与实际提交另行验收，不能用上述工程测试替代模型结果。

后续发现并修正启动排队边界：首次机器人 MCP 已发出、但 Slurm 尚未分配 GPU 时，RPC 日志仍可能为空。新版守护匹配 CLI 的未完成机器人 MCP 调用，不因此重启模型。`queued_startup_guard_acceptance.json` 的集成检查覆盖首次 MCP 等待、已发出的物理请求，以及完成回复后的同线程静默恢复。Sol 保留原 48999 排队作业；旧版已加载监督进程的维护窗口另存本地记录，模型客户端和桥接未暂停。
