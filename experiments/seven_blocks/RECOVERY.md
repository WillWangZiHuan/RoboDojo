# 长时间无动作时的诊断与恢复

用户于 2026-10-28 要求：遇到长时间卡住应主动排查、自助恢复，不只轮询 PID；记录方法供以后复用。不得把连接中断当作模型主动提交，也不得悄悄重跑一场替代原试次。

## 先分清卡在哪里

同时检查模型事件文件、桥接 `rpc.jsonl`、物理帧时间轴、模型进程和 Slurm 作业。PID 存活不代表模型仍在输出，也不代表机械臂在动作。

- 已发出机器人请求而未收到回复：先检查仿真、规划器和图像传输；不要重放该动作。
- 机器人回复已完成、模型迟迟没有新事件：检查模型连接。最小连通诊断不得接入机器人或给它新的展示提示。
- 请求明确提交后才核验最终场景和完整录像；退出、超时、连接断开均不等于提交。

2026-10-28 的 Astra 案例停在第 53 次工具请求后。独立 Astra 小请求约 14.5 秒正常返回；原长历史请求出现 `Broken pipe` 并转为 HTTP，仍无后续输出。模型列表刷新超时在成功诊断中同样出现，不能据此认定失败原因。会话累计 159 张原始 PNG（56,411,507 字节），原生记录约 79 MB。长历史传输是待验证因素；没有直接证据证明根因一定是网络波动。

## 已验证的持久仿真方式

后续试次使用独立 `sbatch` 作业。批处理包装器以 `O_RDWR` 打开请求 FIFO，自己持有读写两端，再把该描述符传给仿真。任何本地客户端或 SSH 连接退出，都不会给仿真送 EOF。原生 JSONL 回复写入服务器持久文件。`batch_transport.py` 保存回复字节偏移、最新回复及未完成请求；重连接读取既有回复，不盲目重放物理动作。

本地 `agent_bridge.py --transport streamable-http` 仅绑定 `127.0.0.1`。客户端用 `--bridge-url`、`--bridge-output` 连接。控制器和桥接进程均使用 detached `Popen(start_new_session=True)`，日志写入该试次目录。桥接关闭只关闭本地资源；只有显式 submit/stop 或 Slurm 基础设施时限结束物理作业。

2026-10-28 的真实持久性测试：杀掉 Astra 新试次的本地桥接 PID 95647 后，以保存的 allocation 和 transport state 重新连接同一 Slurm 48918。七块状态、关节、TCP、动作数、物理步数、重置次数全部完全一致，且 actions=physics_steps=resets=0。模型启动前未改变初始场景。测试证据为 `astra_20261028_003/persistence_acceptance.json`。

## 静默恢复与上下文

`run_agent.py` 每 5 秒检查实际事件进展。HTTP 模式下连续 600 秒没有模型或桥接新事件，且没有未完成的机器人请求时，结束该模型客户端进程组，再使用原 thread ID 续接。只发送连接恢复和先观察的中性提示，不提供作品、布局或动作建议。每次恢复写入 `transport_recoveries.jsonl`。不限制动作次数、失败次数或恢复次数。

600 秒是基础设施静默恢复阈值；它可能中断很长的静默推理，必须作为运行条件披露，不能称为完全无时间干预。原生上下文压缩阈值设为 60,000 tokens，三模型新正式轮次统一使用。原始事件、轨迹和相机图不因上下文压缩而删改。`check_recovery.py` 用合成客户端验证：有未完成物理请求时不重启；请求完成后可恢复静默客户端并保留原 thread ID；该检查不调用模型或仿真。

若模型控制器本身消失，应从 `process.json` 和原生会话记录核对 thread ID，确认旧客户端退出、写入锁释放后再续接。不要删除线程锁、同时启动两个控制器或用另一个作品替代原目标。若桥接消失但批处理作业仍存活，通过 `--reattach-from` 接回原控制目录，并核对实际场景。

## 启动时等待 Slurm 分配

首次机器人 MCP 调用可能已经开始，但仿真仍在 Slurm 队列中，桥接尚未写入 ready 或 RPC 请求。此时不能把空 RPC 日志判为模型空闲。`run_agent.py` 同时匹配原生 CLI 的 `item.started` / `item.completed` 机器人 MCP 调用 ID；任一调用未完成，就不执行静默重启。`check_recovery.py` 覆盖无 RPC 的首次 MCP 等待、已进入 RPC 的物理请求等待，以及回复完成后的静默恢复。

Sol 的 48999 作业实际遇到 `PENDING (Priority)`。这是资源调度等待，应保留队列位置，不当作网络故障，不重复提交作业。修复发生时旧版监督进程已经加载，因此仅暂时挂起该监督进程，模型客户端和桥接继续运行；独立维护监视器在桥接 ready 或模型退出后自动恢复监督进程。该次维护完整记录于 `sol_20261028_001/startup_guard_maintenance.json`，没有暂停模型、重置环境或改变原始指令。新启动的控制器直接使用上述未完成 MCP 判断，不需要这项运行中维护。

## 本次失败恢复的边界

旧版本使用 SSH+srun stdio，把仿真输入寿命与本地进程链绑定。尝试 sattach 时，旧 stdout 会回放且首行可能截断；只读接管曾证明场景一致。但是结束旧模型进程后，原仿真仍收到 EOF 并关闭。原 Slurm 48825 虽以 0:0 退出，`episode.json` 明确是 `interrupted`，原因为 `input closed without submission`，不能计为主动提交。

因此 sattach 不是该旧架构下经过验证的完整恢复方案，不应照抄。旧轮视频、原始记录和全部恢复失败段独立保留。Astra 新试次从同一初始布局、同一原始指令和全新模型上下文重新开始，不提供旧作品或轨迹；不可把两轮拼成一次无中断实验。

如果物理作业已经结束，先封存录像及中断证据，不能伪称原地续接。根据本任务用户授权可修好问题后独立重试，并在结果中保留全部中断轮次。

提交后核验 `terminal.json`、服务端 `episode.json` 与最终场景；等待视频封装完成，再下载全部三路原始 MP4、帧时间轴和交互记录。完整解码、核对帧数与 SHA-256，生成现实时间版和倍速观看版。旧客户端、冻结桥接和独立 HTTP 桥接只在物理作业结束、视频完整保存后清理。
